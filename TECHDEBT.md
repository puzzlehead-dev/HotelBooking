# Технический долг

Известные ограничения проекта и план их устранения. Проект разработан
как учебный: часть решений принята осознанно для текущего масштаба,
часть запланирована на будущие этапы.

Уровни приоритета: 
**Критичный** (нарушает логику или безопасность),
**Важный** (влияет на поддерживаемость или готовность к продакшену),
**Мелкий** (косметика или «было бы неплохо»).

## Этапы

- **A** — упаковка текущей версии (UML, README, CI, лицензия).
- **B** — рефакторинг под портфолио (интерфейсы, DI, Result-паттерн, логирование).

## Важные

### Пароли хранятся в открытом виде
- **Где:** `User`, `AuthService`.
- **Что:** пароли лежат в `Users.txt` как есть, без хеширования.
- **Почему:** хеширование (BCrypt/Argon2) было вне рамок текущей версии.
- **Влияние:** недопустимо в продакшене; утечка `Users.txt` раскрывает все пароли.
- **Как чинить:** `BCrypt` или `Argon2`, хешировать при регистрации, проверять при входе.
- **Этап:** B.

### Нет интерфейсов и DI-контейнера
- **Где:** все сервисы и репозитории.
- **Что:** конкретные классы собираются вручную в `Program.Main`.
- **Почему:** интерфейсы исключены требованием к текущей версии; DI-контейнер не использовался.
- **Влияние:** трудно подменить реализацию (например, файлы -> база данных); тесты используют реальные репозитории с временными файлами.
- **Как чинить:** выделить `IUserRepository`, `IRoomRepository`, `IRequestRepository`, `INotificationRepository`, `IAuthService` и т.д.; зарегистрировать в `Microsoft.Extensions.DependencyInjection`.
- **Этап:** B.

### Файловое хранилище вместо базы данных
- **Где:** `HotelBooking.Storage`.
- **Что:** данные лежат в `Data/*.txt` с разделителем `|`.
- **Почему:** EF Core не входил в текущую версию.
- **Влияние:** нет транзакций, нет защиты от одновременной записи, полная перезапись файла при каждом сохранении, нет индексов.
- **Как чинить:** SQLite + EF Core, миграции, асинхронный API.
- **Этап:** C.

### Нет логирования
- **Где:** везде.
- **Что:** `skippedCount` из `LoadAll(out int skippedCount)` игнорируется; ошибки парсинга проходят молча.
- **Почему:** логирование было вне рамок текущей версии.
- **Влияние:** скрытая потеря данных при битых строках; нет логов.
- **Как чинить:** `Microsoft.Extensions.Logging` или Serilog; логировать пропущенные строки с номерами.
- **Этап:** B.

### `Request.AssignRoom` не проверяет статус заявки
- **Где:** `Request.AssignRoom`.
- **Что:** можно назначить номер заявке в статусе `Rejected` или `Completed`, если вызвать метод напрямую.
- **Почему:** инвариант защищён в `RequestService.Accept`, а не в домене.
- **Влияние:** домен не самовалидируется; будущий вызов может сломать инвариант.
- **Как чинить:** добавить проверку статуса в `AssignRoom`; для десериализации в `RequestRepository` использовать внутренний `ForceAssignRoom`.
- **Этап:** B.

## Мелкие

### Namespace'ы не совпадают с папками в тестах
- **Где:** `HotelBooking.Tests`.
- **Что:** все тесты используют namespace `HotelBooking.Tests` независимо от папки (`Domain/`, `Services/`, `Storage/`, `Fakes/`).
- **Почему:** прагматичный выбор, чтобы не переписывать ~20 файлов.
- **Влияние:** namespace не отражает структуру; чуть хуже навигация по тестам проекта.
- **Как чинить:** либо переименовать namespace'ы в `HotelBooking.Tests.Domain` и т.д., либо оставить как есть.
- **Этап:** B (опционально, не крашит проект).

### Папки с точкой в имени
- **Где:** `HotelBooking.Domain`, `HotelBooking.Storage`, `HotelBooking.Services`, `HotelBooking.UIConsole`.
- **Что:** папки названы как проекты, но физически лежат внутри одного `.csproj`.
- **Почему:** это логические слои с самого начала; разделение на отдельные `.csproj` не делалось.
- **Влияние:** визуально выглядит как multi-project solution, но это не так.
- **Как чинить:** разделить на отдельные `.csproj` (Domain, Storage, Services, UIConsole) на этапе B.
- **Этап:** B.

### Имя `IsDateInFuture` вводит в заблуждение
- **Где:** `BookingService.IsDateInFuture`.
- **Что:** возвращает `date >= Today`, то есть «сегодня или позже», а не «строго в будущем».
- **Почему:** метод создавался для проверки «дата не в прошлом», но имя читается как «строго в будущем».
- **Как чинить:** переименовать в `IsDateTodayOrLater`, либо изменить проверку на `date > Today` и обновить вызовы.
- **Этап:** B.

### Смешанный стиль обработки ошибок в `AuthService`
- **Где:** `AuthService`.
- **Что:** `Register` бросает исключения, `TryLogin` возвращает `bool`.
- **Почему:** `Register` бросает исключения (бизнес-ошибка), `TryLogin` возвращает `bool` (ожидаемый сценарий «не вошёл»). Два разных случая — два разных стиля.
- **Влияние:** непоследовательный API; вызывающий код должен обрабатывать оба стиля.
- **Как чинить:** Result-паттерн, либо всё к исключениям, либо всё к `Try*`-методам.
- **Этап:** B.

### Нет ограничения попыток входа
- **Где:** `AuthService`.
- **Что:** число попыток входа не ограничено.
- **Почему:** вне рамок текущей версии.
- **Влияние:** удобно для перебора пароля.
- **Как чинить:** счётчик попыток на пользователя, задержка или блокировка.
- **Этап:** C.

### Имена пользователей чувствительны к регистру
- **Где:** `User`, `UserRepository`, `AuthService`.
- **Что:** `Alice` и `alice` — разные пользователи.
- **Почему:** осознанное решение.
- **Влияние:** отличается от реальных систем; может удивить пользователя.
- **Как чинить:** нормализовать к нижнему регистру при регистрации и входе.
- **Этап:** B (требуется решение: оставить case-sensitive или case-insensitive).

### Нет проверки длины имени и пароля
- **Где:** `User`.
- **Что:** нет верхней границы на длину имени и пароля.
- **Почему:** в версии на C++ было ограничение <= 15 символов; при переносе на C# проверку убрали как избыточную для текущего масштаба.
- **Влияние:** пользователь может создать имя длиной в терабайт; это ударит по памяти и по файлу.
- **Как чинить:** добавить проверки `MaxLength` в `User` или `AuthService`.
- **Этап:** B (мелкое).

### `UserRepository.SaveAll()` перезаписывает весь файл
- **Где:** `UserRepository.SaveAll`.
- **Что:** каждая регистрация перезаписывает всех пользователей.
- **Почему:** использование txt-файлов как хранилище.
- **Влияние:** O(N) на регистрацию; нормально для сотен, плохо для тысяч.
- **Как чинить:** append-only лог, либо переход на базу данных.
- **Этап:** C.

### Репозитории не проверяют `filePath` на null
- **Где:** конструкторы репозиториев.
- **Что:** `filePath == null` не проверяется.
- **Почему:** ошибка программиста, не пользователя; не входило в текущую версию.
- **Как чинить:** `ArgumentNullException.ThrowIfNull(filePath)`.
- **Этап:** B (мелкое).

## Решено / осознанные решения

Это **не** долг. Записано, чтобы читающий понимал выбор.

- **Пароли в открытом виде** — осознанно, см. «Важные».
- **Имена чувствительны к регистру** — осознанно, см. «Мелкие».
- **Валидация в конструкторах** — оставлена как контракт класса («объект либо валиден, либо не существует»).
- **Без `interface`** — требование к текущей версии.
- **Синхронный API** — асинхронность запланирована на этап C.
- **`Clock` как виртуальный класс** — выбран вместо интерфейса для подмены в тестах.
- **Абстракция `FileStorage` не вводилась** — `System.IO.File` уже абстракция; обёртка была бы переусложнением для этого масштаба.
- **`RoomStatus.Open` как значение по умолчанию** — проверено тестами; новая комната создаётся открытой, это осознанное поведение.
